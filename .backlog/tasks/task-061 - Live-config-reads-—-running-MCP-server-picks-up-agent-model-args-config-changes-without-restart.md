## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
PROBLEM: every agent/model/args setting is startup-frozen in practice, through two mechanisms. (a) Direct: both entry points read .tenet/.state/config.json once at boot (src/mcp/index.ts:17-61, src/cli/serve.ts:29-48) and bake it into JobManager private readonly fields (adviser/defaultAgentModel/gateValidators, job-manager.ts:143-156) and one AdapterRegistry (global *_args baked into adapter constructors, adapters/index.ts:79-85). (b) Indirect: default_agent/agent_override_*/max_retries/timeout_minutes are read LIVE from the SQLite config table at dispatch, but StateStore.loadFileConfig (state-store.ts:1216-1246) syncs file->SQLite only when a WRITABLE StateStore opens (server boot, tenet init --upgrade init.ts:849, or a hidden tenet db cleanup run db-cleanup.ts:345) — the CLI only writes the file, so the DB rows go stale and the "live" reads are frozen too. Net effect: changing the validator/adviser/worker model mid-session requires restarting the MCP server, which usually means restarting the agent session and losing conversation context — bad UX for 12+ hour runs. USER DECISION (2026-11-25): config should be live — the MCP tools read config.json when dispatch is requested; not hard, and correct for the mental model. Consequence of the current freeze already shipping: validator tools' validator_agent/validator_model response fields report from the same frozen config as dispatch (consistent today), but both are boot-stale after any config edit.

SCOPE: one per-dispatch config snapshot for ALL dispatch-relevant surfaces — agent/model pairs (adviser, clarity/readiness gates, default_agent_model), agent selection (default_agent, agent_override_*), adapter args (global + job-scoped), and the scalar keys (max_retries, timeout_minutes) — with config.json as the single source of truth. Also: atomic config writes, CLI torn-read policy, retirement of the loadFileConfig file->SQLite sync + a schema-v3 purge of the stale rows, removal of the restart ritual (hint + restartNeeded), and the doc/skill surfaces that promise restart semantics. OUT OF SCOPE (see MUST NOT TOUCH): making heartbeatTimeoutMs/maxParallelAgents/defaultJobTimeoutMs configurable, reviving tenet_set_agent or adding any MCP write path to config.json, touching runtime-written DB keys (db_schema_version, eval_parallel_safe:<feature>), or changing tenet init's config-preservation rules.

## DESIGN — COLLAPSED RECOMMENDATIONS (one vetoable design; alternatives recorded with why-rejected)

(i) Read primitive: per-dispatch SYNCHRONOUS read of config.json, one snapshot per dispatch. Rejected: fs.watch/mtime cache (file measured ~200-800B, worst 789B; dispatches are seconds-to-minutes apart — a cache buys nothing and adds staleness classes). No watcher exists anywhere in src today.
(ii) Reader home: src/core/runtime-config.ts, next to every existing parser (parseAgentModelConfig/resolveGatePair/parseMaxRetries/parseTimeoutMinutes). Rejected: a CLI-side helper (core must import it; entry points are unimportable by tests so the primitive must live in an importable core module — constraint documented at job-manager.ts:86-97). Consolidates the three duplicated file readers (readStateConfig init.ts:650-660, loadRawStateConfig mcp/index.ts:17-27, loadFileConfig's read state-store.ts:1222-1245) — at minimum the dispatch path uses the new primitive; full consolidation of all three is welcome but not required if it grows the diff.
(iii) loadFileConfig fate: RETIRE the 3-key file->SQLite sync (state-store.ts:1216-1246) for dispatch purposes; dispatch reads the file. Side effects to handle: tenet db cleanup (db-cleanup.ts:345) and tenet init --upgrade (init.ts:849) stop acting as accidental partial-apply buttons (good, but note it); the sync currently never CLEARS DB rows when file keys vanish — stale rows persist until purged.
(iv) Schema v3 purge: versioned migration (src/core/migrations.ts, gated like all real migrations on tenet init --upgrade) deletes default_agent/agent_override_*/max_retries/timeout_minutes rows from the SQLite config table. Why required: history shows agent keys WERE DB-written (tenet_set_agent registered 57e0340 2026-04-08, unregistered e5e48f3 the next day; migration 2 renamed agent_override_playwright_eval IN the DB — DB-resident agent rows were treated as surviving state), and a config.json-less project or a since-removed file key leaves a row that file-only reads would either miss (behavior change vs DB read) or that silently changes dispatch (selectAdapter fail-closes to no-agent if the row was the only default_agent). Rejected: dispatch-time file-then-DB fallback (keeps two sources alive forever — against single-source-of-truth); silent row ignoring (leaves a phantom class of divergence forever).
(v) agent_override_*: file-only after the v3 purge; resolveAgentName reads agent_override_<type> ?? default_agent from the snapshot. The keys remain a phantom knob with no live setter (tenet_set_agent dead code — do not revive; it was removed deliberately so agents cannot switch their own runtime).
(vi) Agent+model pair atomicity: EXECUTION-TIME single-snapshot re-resolution — executeJob takes ONE snapshot, resolves the agent (gate chain / adviser / default path) AND the model (pair pin) from it, updates the job row agent_name for display if it changed. Rejected: persisting {agent, model} on the jobs row (new column + migration + backfill for a seam that a same-snapshot read closes for free). Retry behavior is unchanged in effect: dispatchJob re-resolution already re-resolves per dispatch (job-manager.ts:188-191); execution re-resolution supersedes it consistently.
(vii) Atomic writes: temp-file+rename for writeStateConfig (init.ts:641-648) and the star-nudge RMW (star-nudge.ts:24-31). Precedent: src/cli/db.ts:133,148.
(viii) CLI torn-read policy: abort the edit loudly (non-zero exit, no write) when the CLI's own read fails to parse. Split policy by process role — server: keep-last-good (long-lived process has a snapshot); CLI: cannot keep-last-good (fresh process) and its read is the base of the next whole-file write, so a torn read must abort, never write back.
(ix) Eval-round config-era split: ACCEPT and document — a user editing config mid-round means the round's critics may run in different config eras; verdicts journal their own agent/model (validator response fields), which is the audit trail. Rejected: per-round config snapshots (complexity for a rare case; mid-round edits are operator intent).
Also recorded: adviser retry-stickiness vs gate re-resolution asymmetry is KEPT deliberately (adviser jobs carry an explicit creation-time agent; gates re-resolve per dispatch by design — job-manager.ts:181-191) and must be documented in the pickup semantics.

## DESIGN — PICKUP SEMANTICS (the user-facing contract once the restart ritual is gone)

- Pending jobs pick up config at dispatch. Running jobs NEVER do — argv is frozen at spawn.
- Gate jobs (clarity/readiness) re-resolve their effective pair at every dispatch AND retry; adviser jobs keep their creation-stamped agent (deliberate asymmetry).
- max_retries is stamped per job at creation — a change applies to future jobs only.
- timeout_minutes applies per invocation at execution.
- Validator tools report validator_agent/validator_model from the same snapshot as the executed dispatch.
- Two concurrent server processes converge per dispatch instead of diverging per boot.
- An eval round may split across config eras if the user edits mid-round (accepted; the response fields are the audit trail).
- One user-facing sentence for the README line, modeled on the critics.json precedent (README.md:107): 'Agent, model, args, retry and timeout settings in .tenet/.state/config.json are read live — edits apply from the next dispatched job, no restart.'

## DESIGN — DISPATCH MECHANICS (grounded resolution points; all file:line at the TASK-060 baseline)

Agent resolution happens at SIX points: dispatchJob (job-manager.ts:188-191), startJob (:267-268), createPendingJob (:236), getGateDispatchInfo (:312-340), selectAdapter (:808-824), resolveAgentName (:618-625); the model is computed separately in toInvocation (:970-989); max_retries at getMaxRetries (:220-222) per creation; timeout in toInvocation; args via the frozen registry (getJobExtraArgs). The critical seam: agent stamped on the job row at dispatch (markJobRunning, state-store.ts:602-625) vs model computed one macrotask PLUS one <cli> --version subprocess round-trip later (executeJob -> selectAdapter isAvailable -> toInvocation) — same process, subprocess-sized gap. Today's half-live seams already exist: getGateDispatchInfo (:331-339) and toInvocation (:984) compare the FROZEN defaultAgentModel/pairs against the LIVE SQLite default_agent, so a stale DB row already disables the pinned model silently. The jobs table has agent_name but NO model column; the judging model is recorded nowhere except the validator tools' response fields. Running jobs are immune (frozen at spawn); pending jobs re-resolve at dispatch — that is exactly where the snapshot plugs in. The three pure factories (parseAgentModelConfig, parseAdapterExtraArgs, jobManagerConfigFromStateConfig) are already re-callable; keep-last-good must be BUILT (every reader today fails to {} on parse error); statePaths is already exported from core for path derivation.

## DESIGN — WRITE/RACE POLICY (server vs CLI)

Writers of config.json are all CLI processes: writeStateConfig (init.ts:641-648, single in-place fs.writeFileSync, no temp+rename/lock/fsync), fresh tenet init (init.ts:808-823, refuses to touch existing .tenet), tenet config interactive menu (index.ts:502 — one whole-file write per edit from a session-long stale copy read once at :999), tenet config flags (index.ts:1186), star-nudge RMW at the end of interactive init/upgrade (star-nudge.ts:24-31). The MCP server NEVER writes the file (tenet_init only scaffolds dirs/templates, tenet-init.ts:45-54). All three readers (readStateConfig, loadRawStateConfig, loadFileConfig) swallow corrupt JSON as {} with no warning — the key design hazard this task fixes: at dispatch time a torn read must mean keep-last-good, not empty, and the CLI reader-is-write-base pattern must abort, not amplify (today a torn read permanently drops keys via the next write-back). No fs.watch or mtime caching exists anywhere; at this file size per-dispatch reads without a cache are the simplest correct design. DB snapshots (tenet db snapshot) exclude config.json — restore-snapshot resurrects stale whitelisted SQLite values against a newer file, a divergence class that direct file reads eliminate.

## DESIGN — DB BOUNDARY (grounded)

SQLite config table (key TEXT PRIMARY KEY, value TEXT NOT NULL, upsert): MUST-STAY keys are db_schema_version (read at every StateStore open for the schema gate, state-store.ts:1410-1415, written on init/migrations) and eval_parallel_safe:<feature> (runtime-written by persistReadinessVerdict job-manager.ts:1226-1230, read live by tenet_start_eval:406) — pure server state with no config.json representation; a pure-file design must not touch them. The only code that ever wrote agent keys to the DB was tenet_set_agent, registered for one day (57e0340 2026-04-08 -> unregistered e5e48f3 2026-04-09; file survives as dead code, zero importers, tools/index.ts:19,60). loadFileConfig started DB-wins default_agent-only (57e0340), flipped to file-wins always-sync next day (026fbe3), grew max_retries (e5e48f3) then timeout_minutes (305a2f7); it NEVER clears DB rows when file keys are absent. No *_model or *_args key has ever been DB-written at any commit — file-only by construction. Verdict (grounded): config.json CAN be the single source of truth for agent/model/args/scalars with the DB keeping only runtime-written keys, given the v3 purge (see design iv) and keep-last-good reads (design iv/viii).

## DESIGN — TEST STRATEGY (deterministic liveness, no watchers/timers/waits)

With a per-dispatch synchronous read, liveness is trivially deterministic: write config.json between two dispatches on the SAME JobManager instance and assert the second picks up the new values — no fs.watch, no mtime cache, no fake timers, no real waits (vitest fake timers exist but zero useFakeTimers in src today). The mid-flight agent/model divergence across the subprocess gap is testable by pausing inside MockAdapter's async isAvailable/invoke and rewriting config.json mid-gap (assert the executed pair stays consistent). Keep-last-good: write malformed JSON mid-test. Missing-file vs malformed-file: distinct cases. v3 purge: make test-migrations. End-to-end liveness: the Tier-1 FakeAdapter harness (src/core/integration.test.ts). Entry points cannot be imported by tests (comment job-manager.ts:86-97) — hence the primitive lives in runtime-config.ts (AC).
